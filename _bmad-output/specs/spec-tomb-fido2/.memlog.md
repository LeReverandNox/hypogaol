- (note) source: _bmad-output/brainstorming/brainstorm-tomb-fido2-2026-07-21/brainstorm-intent.md and its .memlog.md, fully absorbed
- (decision) Why: vision to realize + pain to solve. Cold-storage crisis reliability (bank-safe-once-a-year model) for rarely-accessed sensitive material; replaces the multi-tool memorization burden of cryptsetup+fido2-token+systemd-cryptenroll; TrueCrypt's 2014 shutdown is the cautionary reference for standard-tools-only design
- (capability) CAP-1 intent: user can unlock a LUKS2 volume using a FIDO2 security key via tomb-fido2. success: a user with zero FIDO2 familiarity unlocks a LUKS2 volume on first try after being physically prompted to touch the key, no external docs consulted
- (capability) CAP-2 intent: user can enroll an additional FIDO2 key as an alternate unlock method on an already-unlocked volume (LUKS2 native multi-keyslot, up to 32 slots). success: after enrollment, the volume unlocks with either the original or the newly enrolled key
- (capability) CAP-3 intent: user can revoke a single FIDO2 key's keyslot, removing it as a valid unlock method. success: after revocation, the removed key no longer unlocks the volume while other enrolled keys still do
- (capability) CAP-4 intent: user drives unlock/enroll/revoke/pre-flight-check through one unified CLI instead of separately invoking cryptsetup, fido2-token, and systemd-cryptenroll. success: no workflow in v1 scope requires the user to invoke the three underlying tools directly
- (capability) CAP-5 intent: tool guides the user through every interactive step (e.g. key touch) in plain language assuming zero FIDO2 knowledge. success: prompts and error messages never assume familiarity with FIDO2 terms (e.g. 'Please touch your security key button', not 'Awaiting UP')
- (capability) CAP-6 intent: tool verifies all hard dependencies (LUKS2 FIDO2/hmac-secret support, required binaries, kernel features) before any operation. success: on missing dependency, tool exits cleanly pre-operation with a detailed, actionable error message rather than failing mid-operation
- (capability) CAP-7 intent: user can apply all tomb-fido2 operations (unlock/enroll/revoke) directly to raw physical block devices/partitions, not only file-backed loop devices. success: the same CLI commands work unmodified against a raw partition path and a loop-mounted file, a capability original Tomb never exposed
- (constraint) Standard, low-level, well-tested primitives only: LUKS/dm-crypt + FIDO2 hmac-secret. No proprietary formats, no single-vendor-maintained crypto - rules out any custom key-wrapping or format
- (constraint) Break-glass recoverability: README must document manually unlocking the volume using only bare cryptsetup + fido2-token commands, with zero dependency on the tomb-fido2 binary surviving - rules out any proprietary on-disk metadata the binary alone can interpret
- (constraint) Zero-FIDO2-knowledge UX is mandatory across all prompts and errors, not just the happy path - rules out terse/technical CLI output as a valid default
- (constraint) Physical key presence at the exact moment of unlock is a fixed, non-variable assumption - tool supports exactly what cryptsetup's FIDO2 token mode natively offers, no more
- (constraint) No fallback auth paths: FIDO2 is the exclusive unlock mechanism, no GPG/keyfile fallback - rules out any 'recovery password' or keyfile escape hatch as a built-in feature
- (constraint) Must be a real compiled binary (Go or Rust), not a shell script wrapper
- (constraint) Tool remains entirely unaware of backup strategy: README may recommend 3-2-1-style backup of volumes/keys as a disclaimer only, but no code or feature may touch backup concerns
- (non-goal) Remote/delegated unlock beyond cryptsetup's native FIDO2 token mode is out of scope this time
- (non-goal) Post-quantum-readiness features are out of scope - standard-tools recoverability is considered future-proof enough
- (assumption) Should-Have items (break-glass README procedure, 3-2-1 backup disclaimer) are treated as Constraints in the spec kernel since they bend design/documentation decisions rather than describing tool behavior a capability would test
- (question) Recognized safety gap: input does not address what happens if a user attempts to revoke the last remaining valid keyslot (risk of permanent lockout), despite survivability being the project's central design goal - needs a human decision before CAP-3 is implementation-ready
- (question) Recognized security domain implication: input is silent on handling of decrypted key material in process memory (e.g. zeroing derived secrets, avoiding swap) despite this being a cold-storage security tool for highly sensitive material
