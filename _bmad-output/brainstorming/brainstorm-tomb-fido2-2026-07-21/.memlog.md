- (technique) started One Feature Only
- (idea) The one feature kept: unlock LUKS-encrypted volumes using FIDO2 security keys
- (insight) Design goal isn't a wow-effect unlock experience - it's dead-simple, boring reliability: 'I can trust it with my life'
- (idea) Core use case: cold storage for rarely-accessed, highly sensitive material (master GPG key, password manager backup) - like a bank safe, opened once a year in a crisis, must unlock without hesitation
- (decision) Scope boundary: key/volume backup strategy (3-2-1, spare FIDO2 keys) is the user's responsibility, not the tool's concern - tool stays unaware of it
- (decision) Multi-key enrollment is in scope: supporting multiple FIDO2 keys as alternate unlock methods on the same volume via LUKS2's native multi-keyslot support (up to 32 slots) - still counts as 'the one feature'
- (insight) Tool philosophy: thin, user-friendly abstraction layer over LUKS2 + FIDO2 hmac-secret - not reinventing crypto, just enough sugar to make native LUKS2 features (multi-keyslot enroll/revoke) simple to use
- (idea) Core friction the tool solves: replacing a multi-tool memorization burden (cryptsetup + fido2-token + systemd-cryptenroll, each with their own flags) with one tool, simple commands, simple args - no need to hunt notes or search the web during a crisis
- (technique) started Job to Be Done
- (idea) The job being hired: store sensitive information securely without relying on any third party or external service/tool
- (insight) TrueCrypt's 2014 sudden shutdown is the cautionary reference: for critical use cases, rely on the simplest, lowest-level, most standard, well-tested tools (LUKS/dm-crypt) rather than proprietary or single-vendor-maintained solutions
- (decision) Break-glass requirement: README must document how to manually unlock the volume using only standard cryptsetup + fido2-token commands, with zero dependency on the tomb-fido2 binary itself surviving
- (technique) started Assumption Reversal
- (idea) Assumptions confirmed: (1) FIDO2 key must be physically plugged in at the exact moment of unlock, (2) user must already be somewhat familiar with FIDO2, (3) system must ship a modern enough LUKS version with native FIDO2/hmac-secret support
- (idea) Clear-language UX example: at the touch step, print plain instructions like 'Please touch your security key button' rather than assuming FIDO2 familiarity
- (idea) Pre-flight dependency check: tool verifies all hard dependencies (LUKS2 FIDO2 support, required binaries/kernel features) are present, exits cleanly with a detailed error message if anything is missing
- (decision) Rejected reversal: physical key presence at unlock time is not up for challenge - the tool should support exactly whatever unlocking methods cryptsetup's token/FIDO2 mode natively offers, no more no less
- (technique) started Emerging Tech Collision
- (decision) Post-quantum threat explicitly deprioritized: if classical asymmetric crypto breaks, the world has bigger problems than encrypted volumes - being able to still open volumes and extract data via standard tools is future-proof enough
- (technique) started MoSCoW convergence
- (decision) MoSCoW - MUST: unlock LUKS volumes with FIDO2 key; multi-key enrollment (add keyslot); key revocation (remove single keyslot); one unified CLI replacing cryptsetup+fido2-token+systemd-cryptenroll; plain-language terminal guidance assuming zero FIDO2 knowledge; pre-flight dependency check with clear error exit
- (decision) MoSCoW - SHOULD: README-documented break-glass manual recovery procedure; volume/key backup strategy guidance
- (decision) MoSCoW - WON'T THIS TIME: remote/delegated unlock beyond cryptsetup's native token mode; post-quantum-readiness features
- (decision) Clarified SHOULD: README recommends 3-2-1 backup strategy as a disclaimer/recommendation only - the tool itself remains entirely unaware of backups, no code/feature touches this
- (insight) Synthesis: this is not 'Tomb but modernized' - it's proof Tomb's real innovation (thin wrapper over standard/boring primitives that survives the tool's own death) was primitive-agnostic all along, now re-applied to FIDO2 instead of GPG/keyfiles. Chosen direction: FIDO2-only LUKS2 unlock tool (Go/Rust), scoped per the MUST/SHOULD/WON'T MoSCoW list, crisis-reliability and zero-FIDO2-knowledge UX as the driving design constraints
- (idea) New feature beyond OG Tomb: support LUKS2 directly on physical block devices/partitions, not just file-backed loop devices - a core cryptsetup capability Tomb never exposed
- (decision) MoSCoW update - MUST (added): support LUKS2 on raw physical block devices/partitions in addition to file-backed loop devices
