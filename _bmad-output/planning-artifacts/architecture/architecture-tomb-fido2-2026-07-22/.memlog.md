- (decision) Process boundary: tomb-fido2 is a thin orchestrator over systemd-cryptenroll (enroll), cryptsetup (open/close/luksRemoveKey/token ops), and fido2-token (device listing, pre-flight checks). It does NOT reimplement CTAP2/hmac-secret or LUKS2 keyslot crypto itself — that stays inside cryptsetup's own maintained FIDO2 token plugin. Binds: CAP-1..7. Prevents: reimplementing security-sensitive crypto protocols from scratch; keeps break-glass recoverability trivially true since the binary is genuinely just a wrapper. Bonus: strengthens the memory-hygiene constraint for free since the actual LUKS passphrase/secret is derived+consumed inside cryptsetup's process, never tomb-fido2's, for the unlock path.
- (decision) Language/stack: Rust. Rationale given by user: fits the 'wrapper around other tools' shape and the zeroize/security-tool ecosystem convention (age, rage, sequoia-pgp); Go would have been the pick only if reimplementing crypto ourselves, which we're not (AD-1).
- (direction) User wants well-organized, nicely factorized code with clear abstraction boundaries between parts, tightly scoped — explicit ask for a seam between backend-tool orchestration and CLI/UX layer, so guardrail logic (e.g. last-keyslot block) isn't tangled with process-exec plumbing.
- (decision) Paradigm: Hexagonal / Ports & Adapters. domain/ = pure policy (unlock/enroll/revoke workflows + guardrails, e.g. last-keyslot block), ports/ = traits (LuksBackend, Fido2Backend), adapters/exec/ = real shell-out implementation parsing cryptsetup/systemd-cryptenroll/fido2-token output, cli/ = arg parsing + plain-language UX translation (CAP-5), never touches ports directly. [ADOPTED by user]
- (decision) No side-channel state: tomb-fido2 must never persist its own state (key labels, slot mappings, etc.) in a local sidecar file/db. Anything it needs to remember must be written into the LUKS2 header itself via cryptsetup's token JSON metadata, so break-glass recovery and cross-machine consistency both hold even if the tomb-fido2 binary is gone. [ADOPTED by user]
- (decision) Token JSON schema includes a user-supplied per-key label (e.g. 'YubiKey backup'), written at enroll time, read/displayed at revoke time. [ADOPTED by user]
- (note) Working the deferred secret-hygiene constraint (SPEC: 'best-effort attempt to avoid decrypted key material leaking/persisting in process memory')
- (decision) Secret hygiene resolution: any subprocess invocation that may involve secret entry (existing LUKS passphrase during enroll auth, FIDO2 PIN) runs with inherited/passthrough stdio - tomb-fido2 never captures or pipes that data through its own process memory. Only non-secret output (device lists, credential IDs, labels, exit codes) is captured/parsed. No zeroize/mlock machinery needed since no secret buffer ever exists in-process. [ADOPTED by user] Satisfies SPEC's deferred-to-architect memory-hygiene constraint.

- (decision) Create workflow bootstrap-keyslot lifecycle (CAP-8): generate a random passphrase in-process -> luksFormat with it (transient keyslot) -> luksOpen using that passphrase to get the mapper -> mkfs (via FilesystemBackend) -> systemd-cryptenroll the real FIDO2 key (real keyslot+token) -> remove the transient passphrase keyslot. Binds: CAP-8. Prevents: a bare cryptsetup luksFormat having no seed keyslot at all (impossible), and prevents the transient passphrase surviving anywhere past this workflow (argv, disk, a leftover keyslot) -- it exists only long enough to seed the header and open the mapper for mkfs, then is destroyed on both ends (keyslot removed, in-memory buffer zeroized). [ADOPTED by user]
- (decision) AD-3 amended: the transient bootstrap passphrase in the create workflow (see prior decision) is a scoped, explicit exception to 'no secret buffer ever exists in-process' -- it is the one path where tomb-fido2 itself generates and briefly holds a secret, because there is no user-supplied passphrase to pass through for a brand-new tomb. Adds a rule: this buffer must use 'zeroize' and be wiped immediately after the luksOpen call that consumes it, before mkfs runs. Adds 'zeroize' crate to Stack. Binds: CAP-8. Prevents: this one necessary exception quietly widening into a general excuse to buffer secrets elsewhere in the codebase.
- (decision) Create's transient-keyslot removal reuses the same live-keyslot-count guard primitive as AD-5's revoke guard (not a separate unprotected removal call), even though at that point in create there are always exactly 2 valid slots (transient + newly-enrolled FIDO2) so the guard trivially passes. Binds: CAP-8. Prevents: two independent, potentially-inconsistent implementations of 'remove a keyslot safely' existing in the codebase -- one guarded (revoke), one not (create's cleanup) -- where a future edit to the guard's logic could be applied to only one.
- (decision) Resize workflow ordering (CAP-10): domain::workflows::resize rejects any shrink request before touching any adapter (grow-only is enforced in domain, not left to cryptsetup/resize2fs's own behavior). On a valid grow request: LuksBackend resizes the LUKS2 mapping first, then FilesystemBackend grows the filesystem on the now-larger mapper. Binds: CAP-10. Prevents: growing the filesystem before the underlying mapper has the extra space (which would corrupt or truncate), and prevents a shrink request reaching cryptsetup/resize2fs at all given SPEC's non-goal (grow-only).
- (decision) Read-only unlock (CAP-11): a single read_only: bool parameter enters domain::workflows::unlock (from the CLI flag) and is passed atomically to both LuksBackend::open (cryptsetup luksOpen --readonly, block-device-level) and FilesystemBackend::mount (mount -o ro, filesystem-level) -- there is no code path where only one of the two is set. Binds: CAP-11. Prevents: a partial implementation (e.g. ro mount over a rw dm-crypt mapping) that would satisfy a filesystem-level-only reading of 'read-only' but not SPEC's explicit block-device-level requirement, and prevents a later remount -o rw succeeding since the underlying mapper itself already refuses writes.
- (decision) CAP-9 (close) needs no new AD: it is FilesystemBackend::umount followed by LuksBackend::close, symmetric to unlock's mount+open pairing, already governed by AD-1 (orchestrator) and AD-4 (mandatory preflight first).
