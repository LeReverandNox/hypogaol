# Reviewer Gate v4 — Reconcile spine (AD-14..19) vs. SPEC.md CAP-12..17 + hooks.md

**Verdict:** mostly sound — the new ADs correctly capture most intents/success criteria and the hard-vs-soft hook guardrail distinction — but there are two genuine contradictions between the spine's own stated rules and its described mechanism (read-only-unlock leaking into hooks; exec-hook privilege-dropping left unaddressed), plus several narrower silences worth closing before Epic 4 build starts.

## 1. CONTRADICTION (high) — hooks can fire on read-only unlock despite AD-14 saying they never do

- **SPEC/hooks.md:** hooks.md line 3: "Both mechanisms run only at the `open` and `close` lifecycle points (**not create, resize, or read-only unlock**)." SPEC.md Constraints (line 108) repeats: "Hooks run only at open/close (not create/resize/**read-only-unlock**)."
- **Spine:** AD-14 (line 126) opens by restating this correctly — "Hooks run only at open/close, never at `create`/`resize`/read-only-unlock, per hooks.md" — but the *mechanism* it describes doesn't actually enforce the carve-out. AD-11 (line 104-108) establishes that read-only unlock is **the same `domain::workflows::unlock` function**, not a separate one, and AD-4 (line 62) reiterates "including its read-only variant, which is the same `domain::workflows::unlock` function (AD-11), not a separate one." AD-14's rule then gives `unlock`/`close` a single `skip_hooks: bool` parameter and says hooks run "on open (after `FilesystemBackend::mount` succeeds)" whenever `skip_hooks` is false — with no mention of `read_only` at all.
- **Gap:** nothing in AD-14's rule makes `read_only == true` imply hooks are skipped. As written, a plain `unlock --read-only` call (with `skip_hooks` left at its default `false`) would still bind-mount hooks and run exec-hooks — directly contradicting the constraint the spine itself quotes one sentence earlier. Either AD-14 needs an explicit clause ("hooks are gated on `!read_only && !skip_hooks`," or read-only unlock forces `skip_hooks = true` internally regardless of the caller's flag), or AD-11's unification of the two unlock variants needs a documented interaction with AD-14 that currently doesn't exist.

## 2. CONTRADICTION / SILENCE (high) — exec-hooks' "never elevated privilege" constraint has no mechanism

- **SPEC.md Constraints (line 108):** "exec-hooks always runs as the invoking user, **never with elevated privilege, regardless of what privilege the lifecycle step itself needed**."
- **Spine:** AD-14's `hook_file_metadata` check (regular file, executable bit, owned by invoking user or root, not world-writable) verifies properties of the *hook file*, and `run_hook(path, args)` is described purely as an execution call. Nowhere in AD-14, the Structural Seed, or any other AD is there a mechanism for **dropping privilege before invoking `run_hook`** when the process itself is running elevated.
- **Why this matters:** the constraint's own wording ("regardless of what privilege the lifecycle step itself needed") presupposes that some lifecycle steps (at minimum `cryptsetup luksOpen`, `mount`) run with elevated privilege — which on Linux they normally must, whether via the user invoking the whole CLI under `sudo`, a setuid binary, or polkit. If tomb-fido2's process itself runs as root for those calls, then `adapters::exec`'s `run_hook` as currently specified (just shell out to the hook path) would execute the hook as root too, silently violating this constraint. The spine has no privilege model anywhere (no AD discusses how root-requiring subprocess calls are obtained — sudo wrapper, setuid, capabilities, or otherwise), so there is no described mechanism (`setuid()`/`seteuid()` to the real/invoking uid, `sudo -u`, `su`, or similar) for `run_hook` specifically to drop back down. This should be called out as an explicit rule on AD-14 (or a new cross-cutting AD on privilege handling), not left implicit.

## 3. SILENCE (medium) — CAP-12's "technical info about a tomb" narrowed to key-listing only

- **SPEC.md CAP-12 intent (line 64):** "User can view **technical info about a tomb, including** its currently enrolled FIDO2 keys with their labels..." — the "including" phrasing implies enrolled keys are one part of a broader info surface.
- **Spine AD-15 (line 128-132):** `domain::workflows::info(path)` calls `preflight` then `LuksBackend::list_fido2_keyslots(path)` only, returning `KeyslotInfo{keyslot, key_label}` — nothing else. The success criterion (line 65, "shows all currently enrolled FIDO2 keys with their labels... without unlock first") is satisfied, but the broader intent is not addressed: AD-15 is silent on whether `info` also surfaces the `filesystem` type, `credential_id`, or `created_at` fields that AD-2/AD-13's token schema already stores and that a "technical info" command would plausibly want to show (all three are non-secret, already read elsewhere: `filesystem` by resize (AD-10), `created_at`/`credential_id` by revoke's listing (AD-2)). Worth an explicit decision — either state that `info`'s scope is deliberately just the keyslot list (a narrowing of CAP-12's intent) or extend AD-15 to include the other already-available metadata fields.

## 4. SILENCE (medium) — no confirmation that `--skip-hooks` is wired to close-all/slam, not just unlock/close

- **SPEC.md Constraints (line 108):** "an invocation-level option to skip hook processing entirely must exist" — stated generally, not scoped to any one subcommand.
- **Spine:** AD-14 gives `skip_hooks: bool` to `domain::workflows::unlock` and `::close` only. AD-17 (line 144) has `close_all` reuse "AD-8/AD-14's exact single-close sequence (hooks, then umount, then close)" per discovered mapping — implying hooks (and by extension the skip mechanism) apply to close_all/slam too — but neither AD-17 nor AD-18 gives `close_all`/`slam` their own `skip_hooks` parameter, and the Structural Seed's CLI section (line 207) only lists "--skip-hooks (CAP-16)" generically without stating it's threaded through to the `close-all`/`slam` subcommands. Since close_all/slam run the same hook step per mapping, the skip option should demonstrably reach them too — currently the spine doesn't say so explicitly.

## 5. SILENCE / TENSION (medium) — un-timed exec-hooks can defeat slam's "never hangs, moves on" guarantee

- **SPEC.md CAP-15 success (line 77):** slam "escalates signals... stopping once none remain, and it never pauses for confirmation before acting" — framed as a command that reliably makes forward progress through every open tomb.
- **Spine:** AD-8 (line 86) fixes the per-mapping ordering as hooks → `umount` → `close`, and AD-17/AD-18 say `close_all`/`slam` repeat that exact ordering per discovered mapping with no special-casing. AD-18's escalation policy (SIGTERM/SIGHUP/SIGKILL against `processes_using`) only guards the `umount` step. The Deferred section (line 266) separately notes "Hook execution has no timeout (AD-14) — a hanging exec-hooks script blocks open/close indefinitely," but this is stated generically for open/close and never explicitly connected to slam. Since the hooks step runs *before* `umount` in every mapping's close sequence (AD-8), a hanging exec-hooks script on tomb N would block slam from ever reaching `umount`/escalation for tomb N — or for any subsequent tomb in the loop, since AD-17 describes a plain sequential loop with no per-mapping timeout/skip-ahead. This directly undercuts CAP-15's "moving on" framing for the one failure mode (a stuck hook) that slam is arguably most likely to encounter in an emergency. Worth an explicit call-out (e.g. a timeout on `run_hook` for close_all/slam specifically, or an explicit statement that slam always passes `skip_hooks: true` and never runs tomb-authored code during an emergency close).

## 6. SILENCE (low) — `loopback_device` argument undefined for device-backed (non-loop) tombs

- **hooks.md (line 26) / SPEC.md (line 81):** exec-hooks on close is invoked with `close <mountpoint> <tomb-name> <loopback-device> <mapper-device>`.
- **Spine AD-14 (line 126):** `run_hook(path, ["close", mountpoint, tomb_name, loopback_device, mapper_device])` — passed through unchanged from hooks.md's argument list, but CAP-7 (raw device/partition support, pre-Epic-4) means a tomb may have no loop device at all (only file-backed tombs do). Neither SPEC.md/hooks.md nor the spine states what value `loopback_device` takes for a device-backed tomb (empty string, the device path itself, omitted argument, etc.). This predates Epic 4 but Epic 4's hooks feature is the first place it becomes an observable, testable contract detail, and the spine had the opportunity to resolve it (the way AD-16 resolved the open UV question) but didn't.

## Items checked and found consistent (no gap)

- CAP-12/AD-15, CAP-13/AD-16, CAP-14/AD-17, CAP-15/AD-18, CAP-17/AD-19 core intents and success criteria: covered.
- hooks.md's hard-fail-vs-skip-with-warning distinction (bind-hooks soft-skip vs. exec-hooks hard-error) is correctly and explicitly preserved in AD-14 — this is the one guardrail-strictness detail the spine gets exactly right where it would have been easy to blur.
- UV enrollment (CAP-13): AD-16 correctly resolves the SPEC Assumption's open HOW-question (whether `unlock`/`resize` need a new parameter) with a cited, dated resolution, and correctly keeps `user_verification` a sibling field to `CreateTarget` rather than folding it into AD-9's enum.
- Close-all/slam registry-free discovery (CAP-14/15 constraint): AD-17's `list_open_mappings` via `dmsetup ls` + `cryptsetup status` cross-check is a live-query mechanism with no stored registry — matches the constraint.
- Slam's no-confirmation-firing constraint: AD-18 states this explicitly and correctly frames it as an intentional override of the general confirm-before-irreversible-action pattern.
- Slam's TERM → HUP → KILL escalation order and pacing: AD-18 matches CAP-15's success criterion.
