# Story 7.5: Interactive Unlocking-Mode Menu

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a user,
I want to be walked through choosing an unlocking mode when I don't specify one via flags,
so that I can pick without memorizing two separate flags, and discover modes I didn't know existed.

## Acceptance Criteria

1. **Given** I run `enroll` or `create`'s bootstrap step with neither `--user-verification` nor `--client-pin` passed, **when** enrollment reaches the point of resolving unlocking behavior, **then** an interactive menu is shown listing, in order: UV, PIN+UP, UP. [Source: epics.md#Story 7.5, lines 1070-1072]
2. **Given** Story 7.4 reports the connected token as UV-capable, **when** the menu is shown, **then** UV is pre-selected as the default. [Source: epics.md#Story 7.5, lines 1074-1076]
3. **Given** Story 7.4 reports the token as not UV-capable, or the capability check itself errored, **when** the menu is shown, **then** the UV row is still shown, annotated inline with the reason it can't be selected (e.g. "unavailable — this token has no built-in verification" / "could not check: `<error>`"), and the pre-selected default falls to PIN+UP instead. [Source: epics.md#Story 7.5, lines 1078-1080]
4. **Given** UP is selected from the menu, **when** the choice is confirmed, **then** the same security warning as NFR22 is shown before enrollment proceeds. [Source: epics.md#Story 7.5, lines 1082-1084]
5. **Given** at least one of the two flags was passed explicitly, **when** `enroll` or `create`'s bootstrap step runs, **then** the menu is skipped entirely — flags always take precedence over the interactive prompt. [Source: epics.md#Story 7.5, lines 1086-1088]
6. **Given** the menu, **when** it's shown, **then** it uses the same hand-rolled println/stdin prompt convention as device selection (`resolve_interactive_selection`) — no new menu library/dependency. [Source: epics.md#Story 7.5, lines 1090-1092]

**Note (withdrawn scope):** NO-UP was originally a fourth menu row; dropped alongside Story 7.3's withdrawal (Sprint Change Proposal 2026-09-10) — see epics.md Requirements Inventory, FR27/CAP-27. [Source: epics.md#Story 7.5, line 1094]

## Dev Notes

- **Where the menu must live — the single most important design decision in this story.** A naive reading of AC #1 ("when enrollment reaches the point of resolving unlocking behavior") might suggest wiring the menu at the `cli`/`domain::workflows` layer, right where `user_verification`/`client_pin` are first threaded through (mirroring how `fido2_verification_args`'s doc comment frames "the point of resolving unlocking behavior"). **This is wrong for this codebase**: at that layer, no physical FIDO2 device has been selected yet — device selection (`Fido2DeviceSelection::Interactive` or `::Explicit`) only resolves to a concrete hidraw path inside `adapters::exec`'s `resolve_device_selection`, and AC #2/#3 require probing *that specific device's* UV capability (`fido2_token_supports_uv(new_device.path)`) before the menu can even compute its default. The menu must therefore be wired inside `resolve_device_selection`, after device selection resolves and before `print_enroll_pin_warning` — see Task 3. This also means the menu naturally applies uniformly to both `enroll`'s standalone call and `create`'s bootstrap-enroll call, and to both `Interactive` and `Explicit` device-selection modes, since they all converge on this one function already (no duplicated wiring needed, no new `Fido2Backend` port method — consistent with every other Epic 6/7 story's "no new port" pattern, AD-21).
- **A real, known UX consequence of the above: an `Explicit` device selection (scripted `--fido2-device`/`--unlock-fido2-device` use) with no mode flag will now block on an interactive stdin prompt**, where today it silently proceeds with the PIN+UP default. This is what epics.md's AC #5 literally specifies ("Given at least one of the two flags was passed explicitly... the menu is skipped" — explicit *device* selection is not one of "the two flags"), so implement it as written, but call this out explicitly in Completion Notes as a real behavior change worth `LeReverandNox`/John being aware of for any existing automation scripts that pass `--fido2-device` without a mode flag today.
- **NFR22 has never been implemented — this is a real gap, not a "should already exist" assumption.** Story 7.1's own Dev Notes (line 112) explicitly deferred NFR22's warning to what was then "Story 7.2" (the NO-UP-mode story, citing epics.md's then-line-1084). That story was renumbered to 7.3 during this epic's mid-stream restructuring and withdrawn 2026-09-10 with zero code written (Sprint Change Proposal 2026-09-10, story-7.3-withdrawal). No later story picked it up. The warning obligation re-surfaced by inheritance as this story's own AC #4. Grep confirms it: `print_enroll_pin_warning` (the only enroll-time warning function that exists today) only ever discusses *PIN-prompt* behavior, never a standalone "this mode is weaker" statement, and it's gated entirely on `new_device.client_pin` being `true` — a device with **no PIN currently configured** enrolling into UP-only today prints nothing at all. Task 4 closes this for real, for both the menu path (AC #4's literal text) and the pre-existing explicit-`--client-pin=false` CLI path (not literally named by AC #4, but required by NFR22 itself and otherwise permanently unaddressed — see Task 4's own reasoning).
- **Inherited from Story 7.4** (its own Review Findings, deferred explicitly to this story):
  - `fido2_token_supports_uv`'s error message and `fido2_token_has_pin`'s error message are byte-identical in shape (`"fido2-token -I failed for {path}: {stderr}"`) — if this story's menu ever needs to tell a UV-check failure apart from some other failure by message text alone, it can't. In practice this story only calls `fido2_token_supports_uv` (not `fido2_token_has_pin`) at the menu's UV-probe site, so the ambiguity is likely moot here — confirm this holds before treating it as a non-issue.
  - `parse_uv_capable`/`parse_client_pin_configured` both mis-parse non-conformant `options:` formatting (leading whitespace, non-`", "` separators, multiple `options:` lines) as "not capable" rather than surfacing ambiguity — pre-existing, out of this story's scope to fix, but worth knowing the annotated-row "unavailable" text may occasionally be shown for a token that's actually UV-capable but whose `fido2-token` output is oddly formatted.
  - `REAL_INFO_OUTPUT_WITH_PIN` remains the only real-hardware-captured fixture backing UV detection — this story adds no new real capture, so its default-selection unit tests (Task 5) should reuse it via the same technique Story 7.4 established, not invent a new synthetic baseline unnecessarily.
- **Interaction with AD-16's existing precedence:** `fido2_verification_args` already unconditionally forces `client_pin` effectively to `false` whenever `user_verification == true` (a fingerprint/PIN check on-device defeats the point of also requiring a host-typed PIN). The menu's UV selection maps to `(true, None)` — this is consistent and needs no special-casing; `fido2_verification_args` already handles a `user_verification=true, client_pin=None` pair correctly (it only reads `client_pin` in the `else` branch).
- **No architecture-spine amendment authored by prior Epic 7 stories for CAP-28** (Story 7.4 flagged this explicitly, deferring the call to whoever implements the actual menu). This story is the one Story 7.4 meant — implement per epics.md's Requirements Inventory candidate note (line 111) directly, same as 7.1/7.2/7.4 did for their own CAPs; state plainly in Completion Notes that no formal AD was authored, for Winston to retcon later if he wants Epic 7's design formally recorded (a real architectural decision *was* made here — where the menu lives, described above — so this is a better candidate for a real AD-22 than any of 7.1/7.2/7.4 were).
