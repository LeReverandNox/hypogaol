# Story 7.2: Mount-Point Creation Resilient to Pre-Existing `/run/media` Ownership

Status: review

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a user,
I want unlock's mount-point directory creation to succeed regardless of what already owns `/run/media/<username>`,
so that unlocking works the same whether or not a desktop mount manager (udisks2/gvfs) is running on my machine.

## Acceptance Criteria

1. **Given** `/run/media/<username>` does not yet exist, **when** `unlock` mounts a volume, **then** behavior is unchanged from today — it's created and the per-volume mount point is chowned to the invoking user. [Source: epics.md#Story 7.2, lines 1018-1020]
2. **Given** `/run/media/<username>` already exists, owned by another user or root (e.g. pre-created by udisks2/gvfs at `751 root:root`), **when** `unlock` mounts a volume, **then** the per-volume mount-point directory is still created successfully — via an unconditionally privileged `mkdir` + `chown` of the leaf directory to the invoking user, regardless of the parent directory's ownership — and mount proceeds normally. [Source: epics.md#Story 7.2, lines 1022-1024]
3. **Given** the per-volume mount-point directory name is already in use (collision), under either ownership scenario above, **when** `create_mount_point`'s retry logic runs, **then** the existing basename-then-suffixed-retry collision behavior (Story 1.9, AC #2) is unchanged. [Source: epics.md#Story 7.2, lines 1026-1028]
4. **Given** this fix, **when** implemented, **then** it does not attempt to change ownership or ACLs of the shared `/run/media/<username>` parent directory itself — mount succeeding and the volume being accessible to the invoking user is sufficient (declined porting `dyne/tomb`'s ACL-on-parent behavior). [Source: epics.md#Story 7.2, lines 1030-1032]

- [x] **Task 1: Make `create_mount_point`'s leaf directory creation unconditionally privileged** (AC #1, #2)
  - Change `create_mount_point`'s signature from `fn create_mount_point(base: &Path, volume_name: &str) -> Result<PathBuf, DomainError>` to also accept the invoking identity: `fn create_mount_point(base: &Path, volume_name: &str, identity: &InvokingIdentity) -> Result<PathBuf, DomainError>`. `mount()` already computes `identity` once up front (line 2851, reused for the base-dir bootstrap and the post-mount chown) — thread that same value into the new parameter at the call site (line 2903), no second `invoking_identity()` call.
  - Replace the loop body's `std::fs::create_dir(&candidate)` with `privileged("mkdir").arg(&candidate).output()` (no `-p` — the leaf's parent, `base`, is already guaranteed to exist by the time `create_mount_point` is called, either pre-existing or just bootstrapped by `mount()`'s own untouched `base.exists()` block). Mirror `with_transient_mount`'s `Command`-output error-handling shape (lines 2292-2311), not `std::fs::create_dir`'s `io::Result`/`ErrorKind` shape — a `sudo mkdir` failure is a `Command` output with a non-zero exit and stderr text, not an `io::Error`.

- [x] **Task 2: Chown the leaf directory to the invoking user after every successful privileged mkdir** (AC #1, #2 — the critical, easy-to-miss correctness requirement)
  - **This is new work `create_mount_point` did not need before this story.** Today, the leaf is created via unprivileged `std::fs::create_dir`, which runs as the invoking (unprivileged) process — so the created directory is naturally already owned by the invoking user, no explicit chown required. Once directory creation goes through `sudo mkdir` (Task 1), the new directory is root-owned instead, because it was created by root. **If this task is skipped, AC #1's "behavior is unchanged from today" silently regresses** — a mount-point that used to end up user-owned (the base-didn't-exist case, which currently works and must keep working) would come out root-owned, breaking every plain unlock, not just the udisks2 scenario this story targets.
  - After each successful `privileged("mkdir")` (both the first-attempt-succeeds branch and any collision-retry-succeeds branch — every path that returns `Ok(candidate)`), immediately run `privileged("chown").arg(format!("{}:{}", identity.uid, identity.gid)).arg(&candidate).output()` and propagate a `DomainError::AdapterFailure` on failure, mirroring the base-dir chown's existing error-message shape (line ~2894-2900).
  - The leaf directory's own permission *mode* does not need an explicit `-m` flag on the `mkdir` — unlike `with_transient_mount`'s scratch directories (which are used directly, `-m 0700`), this leaf is only ever a mount anchor: `mount()`'s existing post-mount `chmod 0700` (line 3032) and the mounted filesystem's own root-inode permissions fully supersede whatever mode the empty pre-mount directory had. Don't add mode-setting logic that duplicates that later step.

- [x] **Task 3: Preserve the collision-retry loop's exact shape and AC #3's guarantee, without relying on `io::ErrorKind`** (AC #3)
  - `Command` output has no `io::ErrorKind::AlreadyExists` equivalent — a failed `sudo mkdir` on an existing path is just a non-zero exit with some stderr text. **Do not parse `mkdir`'s stderr for "File exists"** — that string is locale-dependent (GNU coreutils localizes it) and brittle across `mkdir` implementations/versions. Instead, on any privileged-mkdir failure, cheaply re-stat the candidate path with an *unprivileged* read (`std::fs::symlink_metadata(&candidate).is_ok()`) to distinguish "it already exists → this is the expected collision, retry" from "it still doesn't exist → this is a genuine failure (disk full, `base` itself unwritable to root for some reason, etc.), propagate immediately" — no `sudo` needed for a read-only stat.
  - Keep `MAX_ATTEMPTS = 3` and the exact suffix-retry shape (`random_hex_suffix()`, `&suffix[..4]`) unchanged. On exhaustion, keep the existing `"could not find an available mount point under {base} after {MAX_ATTEMPTS} attempts"` `AdapterFailure` text unchanged (AC #3: "unchanged").

## Dev Notes

- **Root cause (from the sprint-change-proposal, don't re-derive):** `FilesystemBackend::mount`'s `base.exists()` guard (line 2865) only privilege-fixes `/run/media/<username>`'s ownership when the directory is *entirely absent*. When udisks2/gvfs pre-creates and owns it as `751 root:root`, the guard is skipped, and `create_mount_point`'s then-unprivileged `std::fs::create_dir` fails with `EACCES` — surfacing to the user as the generic "couldn't mount its filesystem" message (the failure text contains the substring "mount", so `ux.rs`'s generic mount-failure bucket swallows the real cause). [Source: _bmad-output/planning-artifacts/sprint-change-proposal-2026-09-10.md §1]
- **This is a regression of a fix Story 1.9 claimed but never actually implemented** — its review record marked the identical fix (a uid-stat-based guard instead of `base.exists()`) `[x]` as done; `git blame` on the current code disproves it. The same story's record also falsely claims fast unit-test coverage for `create_mount_point`'s collision logic exists. **Neither claim should be trusted** — this story's Task 0 already reverified both independently; don't re-litigate, just don't propagate the pattern by marking something "done" here without an equally-verifiable citation (file:line, a passing test name, a command's real output). An open, unassigned `sprint-status.yaml` action item (epic 7) proposes requiring exactly that discipline for future code-review "fixed" claims — not this story's job to resolve, just context for why Task 0 is unusually skeptical.
- **Story 7.1's own Dev Notes reference "Story 7.2" several times** (e.g. "a later story (7.2...) can build a three-flag precedence table", "NFR22... written into Story 7.2's acceptance criteria") — those were written *before* this correct-course renumbering and refer to what is now **Story 7.3** (Touchless Enrollment & Flag Precedence, NO-UP mode), not this story. This story (the real, current 7.2) is an unrelated mount-point ownership bug fix inserted between 7.1 and the renumbered 7.3. Don't let those stale cross-references cause confusion when reading 7.1's file for other context.
- **Scope is deliberately narrow** — single adapter-layer function (`create_mount_point`) plus one call-site parameter addition (`mount`). No port signature change (`create_mount_point` is a private, non-trait `adapters::exec` function — confirmed via grep, no other call sites exist anywhere in `src/` or `tests/`), no domain-layer change, no new `DomainError` variant (mirror the existing `AdapterFailure` formatting already used for the base mkdir/chown failures), no CLI change. Effort/Risk both assessed **Low** in the sprint-change-proposal — keep it that way; resist scope creep (e.g. don't also fix the pre-existing swallowed-cleanup-failure pattern under a root-owned parent noted below, or the base directory's own ACLs — both explicitly out of scope).
- **A pre-existing, unrelated limitation worth knowing about (not this story's to fix):** every cleanup path in `mount()` after a leaf directory is created (mount fails, chown fails, chmod fails) calls unprivileged `std::fs::remove_dir(&mountpoint)`. Removing a directory *entry* requires write+execute permission on its *parent*, not ownership of the child — so under AC #2's exact scenario (`751 root:root` parent), the invoking user's process cannot itself unlink that entry even after this story's fix chowns the leaf to them, leaving an orphaned empty directory on any failure after creation. This is the same pre-existing "swallowed compensating-cleanup failure" pattern Story 1.9's own Dev Notes already flagged and deferred (its line 62 finding) — this story doesn't change that calculus and shouldn't try to fix it as a drive-by.
- **No architecture-spine change needed** — confirmed via the sprint-change-proposal (§2, Architecture conflict: None). AD-12 (deterministic mapping name and mountpoint discovery, no registry) is unaffected: this story changes *how* the mount-point directory gets created, never *where* it lives or how it's later rediscovered (`findmnt`-based, AD-12, untouched). [Source: architecture/architecture-tomb-fido2-2026-07-22/ARCHITECTURE-SPINE.md#AD-12, line 119]
- **Testing-strategy note (AD-7):** this story moves `create_mount_point` from "pure filesystem code" to "needs `sudo`" — it now joins `with_transient_mount` as adapter logic only the hardware-gated suite can fully exercise. Task 6's pure-helper extraction is the recommended way to still get *some* fast-suite coverage of the naming/retry-sequence logic without requiring `sudo` inside `cargo test --lib`, which would break the default unprivileged CI run.
