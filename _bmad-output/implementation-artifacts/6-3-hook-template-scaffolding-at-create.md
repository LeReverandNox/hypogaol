# Story 6.3: Hook-Template Scaffolding at Create

Status: ready-for-dev

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a user,
I want create to optionally scaffold example bind-hooks/exec-hooks files into a new volume,
so that I can discover the hooks format without consulting docs first.

## Acceptance Criteria

1. **Given** I run create with the scaffold-hooks flag, **when** creation completes, **then** the volume contains a commented-out example `bind-hooks` file (parses to zero live entries) and a non-executable `exec-hooks.example` stub — not the live `exec-hooks` filename. [Source: epics.md#Story 6.3, lines 826-828]
2. **Given** I run create without the flag (default), **when** creation completes, **then** no template files are written. [Source: epics.md#Story 6.3, lines 830-832]
3. **Given** scaffold-hooks is requested, **when** create runs, **then** scaffolding happens after `mkfs` (so a filesystem exists to hold the files) and before final marker/keyslot cleanup, via a mount → write → unmount sequence on the still-open mapper — no separate FIDO2 selection needed. [Source: epics.md#Story 6.3, lines 834-836]
4. **Given** a scaffolded volume, **when** I later rename `exec-hooks.example` to `exec-hooks` and `chmod +x` it, **then** it activates as a normal exec-hooks file, passing AD-14's existing guardrail checks. [Source: epics.md#Story 6.3, lines 838-840]

## Dev Notes

- **No new port, no new architectural layer.** This story adds one new method (`scaffold_hook_templates`) to the existing `FilesystemBackend` port — already anticipated by name in the Structural Seed (`ARCHITECTURE-SPINE.md:240`) — following the exact same "extend, don't add a 4th port" precedent AD-14 already established for the other hook-related methods (`bind_mount`, `hook_file_metadata`, `run_hook`, `invoking_home_dir`). [Source: architecture/architecture-tomb-fido2-2026-07-22/ARCHITECTURE-SPINE.md:38, :89, :132-136, :240]
- **`scaffold_hooks: bool` is a sibling to `CreateTarget`, never embedded inside it** — same AD-9 Rule Story 6.2's `key_label` already followed: "`scaffold_hooks: bool` (CAP-19, default `false`)... are all siblings to `CreateTarget` in the signature, never embedded inside it." [Source: architecture/architecture-tomb-fido2-2026-07-22/ARCHITECTURE-SPINE.md:95]
- **Real execution order is load-bearing and explicit in AD-9's Rule**: FIDO2 enrollment → `mkfs` → (if `scaffold_hooks`) mount → `scaffold_hook_templates` → unmount → remove marker token → remove bootstrap keyslot. Scaffolding must land strictly after `mkfs` (a filesystem must exist to hold the files) and strictly before final marker/keyslot cleanup (AC #3) — inserting it anywhere else contradicts both AD-9's Rule text and its own "Prevents" clause ("hook-template scaffolding (CAP-19) landing on disk before a filesystem exists to hold it, or after the volume's already locked back up"). [Source: architecture/architecture-tomb-fido2-2026-07-22/ARCHITECTURE-SPINE.md:99-103]
- **`exec-hooks.example`, never the live `exec-hooks` name — this is a hard architectural constraint, not a naming preference.** AD-14's existing guardrail hard-errors `open` on any `exec-hooks` file present but not executable; scaffolding a non-executable stub under the live name would make every scaffolded volume fail to open until the user manually intervened, directly contradicting CAP-19's "discoverable, not broken" intent. `bind-hooks` keeps its live filename since AD-14 only inspects *parsed* entries, and a fully-commented-out file parses to zero — inert by content, not by name. [Source: architecture/architecture-tomb-fido2-2026-07-22/ARCHITECTURE-SPINE.md:103]
- **The "parses to zero live entries" property comes for free from the existing `parse_bind_hooks` implementation** — a `#`-prefixed example line is 3 whitespace-separated tokens, and `parse_bind_hooks` already silently drops any line that isn't exactly 2. No comment-syntax awareness needs to be added to the parser; do not modify `parse_bind_hooks`. [Source: src/domain/hooks.rs:66-87, read in full during story creation]
- **The mount → write → unmount step must clean up on its own failure, or the outer `luks.close` misreports the real error.** `bootstrap_and_provision` unconditionally calls `luks.close(&mapper)` after `finish_provisioning` returns, on both `Ok` and `Err` — if the scaffolding step leaves the mapper mounted on an error path, that `luks.close` call fails with a confusing "device busy" error instead of surfacing what actually went wrong. Task 4's `match fs.umount(mapper) { ... }` block mirrors `bootstrap_and_provision`'s own existing `Ok(()) => luks.close(...)`, `Err(err) => ... err.with_rollback_cleanup_failure(close_err)` shape, applied one level down for `umount`. [Source: src/domain/workflows/create.rs:215-221, read in full during story creation]
- **`scaffold_hook_templates` runs unprivileged, deliberately, same reasoning as `run_hook`/`invoking_home_dir`.** This whole process never runs elevated as a whole — only individual `privileged()`-wrapped subprocess calls escalate. `mount`'s own implementation already `chown`s the mountpoint to the invoking user and `chmod 0700`s it before returning, so a plain `std::fs::write` from this same unprivileged process succeeds with no escalation needed — do not wrap this in `privileged()`. [Source: src/adapters/exec/mod.rs, `mount`/`run_hook`/`invoking_home_dir` implementations, read in full during story creation; architecture/architecture-tomb-fido2-2026-07-22/ARCHITECTURE-SPINE.md:132-136]
- **No new `preflight` dependency check needed.** `scaffold_hook_templates` uses only `std::fs::write` — no new external binary, unlike e.g. Story 6.4's `xfsprogs`/`btrfs-progs` additions elsewhere in Epic 6. Do not add anything to `domain::preflight` for this story.
