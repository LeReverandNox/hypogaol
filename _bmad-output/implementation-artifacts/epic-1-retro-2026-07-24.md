## What Went Well

- **AD-7's fakes/testing discipline held up exactly as designed**: one shared fakes module (`tests/unit/fakes.rs`), extended in place by every story from 1.4 onward, never duplicated or reinvented.
- **Scope discipline across stories**: later stories consistently declined to speculatively widen earlier signatures (e.g. Story 1.7 explicitly held off adding a `read_only` param the architecture hinted at, leaving it for Story 3.3).
- **Story 1.5 proactively originated the shared last-keyslot guard and enroll mechanics generically**, even though AD-5's prose assumed they'd already exist — this means Epic 2 (2.1/2.2) inherits working, hardware-verified primitives rather than starting from scratch.
- **Real user testing of the compiled binary, not just code review, drove concrete fixes**: Story 1.5's three post-review UX fixes (scoped `sudo` via a `privileged()` helper, closing the mapping instead of leaking it, K/M/G/T size suffixes) all came from trying the actual binary.

## What Didn't Go As Smoothly

- **Repeated wrong assumptions about `cryptsetup`'s real CLI behavior, caught only by hardware runs, not by the architecture doc or unit tests:**
  - Story 1.5: `systemd-cryptenroll` hangs on piped non-tty stdin (fixed via `--unlock-key-file`); the last-keyslot guard wrongly blocked removing the never-valid transient bootstrap keyslot.
  - Story 1.6: `cryptsetup luksFormat --size` doesn't exist on the installed cryptsetup version at all (architecture assumed it did) → pivoted to `resize --device-size`; that then failed because the LUKS2 keyring lookup doesn't cross separate `sudo` invocations → switched to `--key-file -`; the hardware test's own headroom assertion was then found to be checking the wrong thing, since LUKS2 segment size is by-design `"dynamic"`.
  - Story 1.7: found a *pre-existing* Story 1.6 bug — `resize` was being called even with zero headroom (size == full raw capacity), which fails outright.
  - **Lesson (Winston):** any architecture-level claim about external tool behavior should get a throwaway empirical spike before a story signature locks in around it — not just a citation to a man page.
- **A security fix introduced a new bug that only surfaced in real usage, discovered by the Project Lead post-epic**: Story 1.7's review flagged the mount point as world-readable and fixed it with `chmod 0700` — but since `mount`/`mkfs.ext4` both run via `sudo`, the directory ends up root-owned, so 0700 makes the tomb accessible to root only, not the invoking user. The fix was verified against the vulnerability it closed, not against the actual use case.
- **A story's status metadata went stale after merge**: Story 1.4's file still reads `Status: review` despite PR #8 being merged weeks ago and sprint-status.yaml correctly showing `done`.

## Post-Epic Findings (surfaced by the Project Lead's own testing, resolved in this retrospective)

1. **Mount-point ownership bug** — `mount()`/`chmod 0700` run as root with no `chown` step, so the unlocked tomb is inaccessible to the actual invoking user. Confirmed in code at `src/adapters/exec/mod.rs:937`.
2. **Mount location** — currently `/tmp`, not visible in a file explorer. Agreed: move to `/run/media/<username>/<tomb-name>` (matching `dyne/tomb`/udisks2 convention), creating the base directory once with correct ownership.
3. **CLI ergonomics** — `--path` should be positional, not a flag, on `create file`, `create device`, and `unlock`.

**Design decision reached:** keep the dm-crypt mapping name unchanged (`vault-<16-hex-hash>`, per AD-12's uniqueness requirement — a pure basename isn't collision-safe as an internal mapping identity). Only the user-visible mount folder name changes, derived from the source basename (extension stripped for file-backed targets), falling back to a short disambiguating suffix only on a name collision.
