# Story 2.1: Enroll an Additional FIDO2 Key

Status: ready-for-dev

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a user with an already-created tomb,
I want to enroll an additional FIDO2 key as an alternate unlock method,
so that I have a backup way to unlock my tomb if I lose my primary key.

## Acceptance Criteria

1. **Given** an existing tomb with one enrolled FIDO2 key, **when** I run the enroll command with a second physical key and touch it when prompted, **then** a new LUKS2 keyslot is created and a `systemd-fido2` token is written with generic `key_label`/`credential_id`/`created_at` metadata, **and** these fields are never prefixed with the product's placeholder name. [Source: epics.md#Story 2.1; AD-2, AD-13]
2. **Given** the tomb now has two enrolled keys, **when** I unlock with either the original or the newly enrolled key, **then** the volume unlocks successfully with either one. [Source: epics.md#Story 2.1]
3. **Given** LUKS2's native multi-keyslot support (up to 32 slots), **when** enrolling, **then** the operation works within that limit, **and** enroll runs `domain::preflight` first like every other workflow. [Source: epics.md#Story 2.1; AD-4]
4. **Given** the enroll workflow needs an existing-passphrase or FIDO2 PIN prompt, **when** any such secret entry occurs, **then** it runs with inherited/passthrough stdio, never captured by the tool's own process, **and** it is always a separate subprocess call from any non-secret credential-id lookup (e.g. `fido2-token -L`). [Source: epics.md#Story 2.1; AD-3]
5. **Given** an existing tomb on a raw device/partition instead of a loop-backed file, **when** I run the enroll command, **then** the identical command works unmodified — enroll makes no branching decision based on target type, consistent with the deterministic mapping-name/mountpoint discovery (AD-12). [Source: epics.md#Story 2.1; AD-12]

## Dev Notes

- **The two real gaps are Tasks 1 and 3, not the domain workflow itself.** `domain::workflows::enroll::run` (Task 2) is a thin, mostly-mechanical orchestration once Tasks 1 and 3 exist — most of this story's actual risk lives in `adapters::exec`'s existing `enroll_fido2_key`, which was built *only* for create's bootstrap case (Story 1.5) and silently assumes a transient passphrase always exists. Don't treat Task 2 as the hard part; it isn't.
- **SUPERSEDED (see "Architect consultation resolved" below).** This bullet originally said no port/signature changes were needed. That no longer holds: `Fido2Backend::enroll_fido2_key` gains a `Fido2DeviceSelection` parameter to fix a real hardware bug, and the user explicitly approved this deviation from "no signature changes" — v1 is still under active development, and a small, forced, mechanical signature change beats leaving a known device-selection race in place. Kept here (rather than deleted) so the reasoning for the original constraint, and why it was consciously overridden, stays visible.
- **Enroll never opens or mounts the tomb.** `systemd-cryptenroll`/`cryptsetup token export|import` all operate on the LUKS2 header at the container path directly — there is no `LuksBackend::open` or `FilesystemBackend::mount` call anywhere in this workflow. This is also *why* AC #5 (raw device vs. loop file parity) requires no code: there's no target-type branch to have gotten wrong in the first place.
- **`Filesystem` has exactly one variant (`Ext4`) today (AD-8).** Hardcode it in `KeyMetadata` rather than adding a CLI flag or a new read-back mechanism — there's no ambiguity to resolve yet. This mirrors how `bootstrap_format_and_open`'s own `filesystem` parameter is currently a no-op (`src/adapters/exec/mod.rs:536-537`) for the identical reason.
- **AD-3 compliance for Task 3's new branch:** the existing-key authentication prompt (touch/PIN) must never be captured by this process — inherited stdio via `.status()`, exactly like `LuksBackend::open`'s existing call (`src/adapters/exec/mod.rs:772-779`), not `.output()` (which would capture and buffer it). This is a separate subprocess invocation from any non-secret lookup (e.g. a future `fido2-token -L` call) — there is no such lookup in this story's scope today, but if one is added later it must stay a distinct call, never combined with the enrollment call itself.
- **Known, deferred, not this story's job to fix:**
  - `enroll_fido2_key` hardcodes `--fido2-device=auto` (deferred from Story 1.5's review) — with two FIDO2 devices plugged in simultaneously, which one `systemd-cryptenroll` treats as "existing" vs. "new" is ambiguous. The expected UX (matching `systemd-cryptenroll`'s own native prompts) is the user has only the relevant device plugged in at each prompt, swapping when asked. Don't attempt device selection in this story.
  - Device-backed real block devices are typically `root:disk 660` — per Story 1.6's deferred finding, this effectively requires running the whole `tomb-fido2` binary under `sudo` for any device-backed operation, undocumented in `--help` (retro action item #5, unassigned, explicitly "not blocking Epic 2"). This applies identically to a device-backed `enroll`; no new handling needed here, same accepted limitation as `create device`.
- **Previous story's own discipline (1.9) still applies, with one deliberate, user-approved exception:** keep this diff scoped to exactly what the ACs above need, and don't touch `close`/`resize`/`revoke` (still `todo!()` stubs, later stories) or `mapping_name.rs`. `create.rs`'s bootstrap-enroll call site **is** now in scope — see "Architect consultation resolved" below — because it shares `Fido2Backend::enroll_fido2_key` with this story's own change and the signature change forces a call-site update either way; while touching it, `create` also gets the same `Interactive` device-selection treatment and a new scripted `--fido2-device` flag, at the user's explicit request (2026-07-25), not just the minimum forced compile-fix. `unlock.rs` itself still needs no change — its presence-wait fix lives entirely inside `adapters::exec`'s `LuksBackend::open`, no signature touch there.

    - **Conclusion**: passing two distinct hidraw paths (`--fido2-device=<new>`/`--unlock-fido2-device=<existing>`) to a single `systemd-cryptenroll` invocation does not reliably resolve which physical touch authenticates which role — this is a genuine device-selection ambiguity, not a flag typo. Continuing to patch this blind (without hardware access) risks more of the same trial-and-error.

This would also address the pre-existing "no key plugged in" failure mode called out in Dev Notes' deferred-work list. Until that design lands, Task 3's current `None` branch should be treated as **unverified and likely to be reworked**, not production-ready — do not check the final Task 6 hardware-verification box, and do not move Status past `in-progress`.

    - **Architect consultation resolved (Winston, 2026-07-25).** Root cause identified: the paused `None` branch identifies "which physical key is which" via a *temporal diff* (query `fido2-token -L` with only the existing key in, query again after the new key is plugged in, diff the two sets) — inherently racy, and the likely cause of both the observed hang and the native "More than one FIDO device found" error. Replace with a *spatial choice* — list whatever's currently enumerated at one point in time and let the user explicitly assign roles, no diffing. Resolved design, to replace Task 3's `None` branch entirely:
      - `Fido2Backend::enroll_fido2_key` gains one new parameter: `Fido2DeviceSelection { Interactive, Explicit { new: PathBuf, existing: Option<PathBuf> } }`. `domain::workflows::enroll::run` and `domain::workflows::create::run`/`finish_provisioning` both thread it through unchanged — domain stays a dumb passthrough, no device-selection policy leaks into `domain`. `existing` is `Option` rather than required because `create`'s bootstrap call never has (or needs) an existing-key role — its "unlock" side is the transient passphrase, not a second physical device — while enroll's standalone (no-transient-passphrase) path requires `existing: Some(..)` in `Explicit` mode and errors defensively if it's absent there. This is the one deliberate port-signature change this fix needs; everything else stays inside `adapters::exec`.
      - **`create` gets the same treatment (user-approved 2026-07-25, not merely the minimum forced by the signature change):** `finish_provisioning`'s `enroll_fido2_key` call now passes `Interactive` by default, reusing the identical wait/list/pick helper with a **single** role ("which key do you want to use for this tomb?") instead of enroll's two — if exactly one device is present when one is needed, it's auto-picked silently with zero prompt, so today's single-key `create` UX is unchanged; if 2+ are present, the same by-index list-and-single-select appears; if none, the same presence-wait applies (fixing create's own "fails immediately with no key" bug, identical root cause to enroll's and unlock's). `create file`/`create device` also gain a new scripted `--fido2-device <path>` flag, constructing `Explicit { new: <path>, existing: None }` — no `--unlock-fido2-device` flag on `create` (there is no existing-key role to fill). This deliberately widens the story's diff into previously-shipped, Epic-1-stable code (`create.rs`) — see Dev Notes' "Previous story's discipline" bullet above for the explicit scope call.
      - **`Interactive`** (default, no CLI flags given): poll `fido2-token -L` until **at least 2** devices are enumerated (message states how many more are needed, e.g. "found 1 key, plug in a second one" — this also subsumes the "fails immediately if no key plugged in" complaint). Once ≥2 are present, list **all** of them by index (hidraw path + any product/vendor string `fido2-token -L` exposes) and explicitly prompt for **both** roles — "Which is your EXISTING key? [1-N]" then "Which is your NEW key? [1-N]" — never an elimination shortcut ("pick one, assume the other"), so the same code path handles exactly-2 and N>2 uniformly. Reject and re-prompt if the same index is given for both roles. Known, accepted limitation (documented, not engineered around): if 3+ visually-identical keys are plugged in, there is no generic libfido2/`fido2-token` "identify" primitive to tell the user which numbered line is which physical device — instruct the user to unplug extras first if their keys look alike.
      - **`Explicit`** (new flags `--fido2-device <path>` / `--unlock-fido2-device <path>` on `enroll`, all-or-nothing — supplying only one is a CLI parse/validation error, not a partial fallback to `Interactive`): skip the wait/list/prompt entirely; validate the given path is currently enumerated via `fido2-token -L` before calling `systemd-cryptenroll` (fail clearly if not, same before-the-mutating-call discipline as AD-4); pass both paths straight through. Enables unattended/scripted enrollment. Caveat worth a doc/README line: `/dev/hidrawN` numbering isn't stable across reboots/replugs — that's a udev-configuration concern for the caller's environment, not something tomb-fido2 manages itself (same spirit as AD-6: no bespoke device-identity scheme).
      - **`unlock` (`LuksBackend::open`) gets a smaller, separate fix**, decided in the same discussion: add a presence-wait loop inside the adapter — poll until **≥1** FIDO2 device is enumerated (friendly wait message if none yet), no explicit-device flag, no signature change. Cryptsetup's own credential-based `auto` already disambiguates correctly once at least one device is present (confirmed no ambiguity bug there, unlike enroll), so `unlock` needs only the presence-wait, not a picker. **User decision (2026-07-25): skip an explicit `--fido2-device` flag for `unlock` for now** — revisit only if a concrete unattended scenario surfaces where `auto` isn't sufficient.
      - No architecture-spine amendment needed — none of AD-1/2/3/6 are violated (enumeration stays non-secret per AD-3; the presence-wait loop delays *invoking* cryptsetup rather than configuring its own touch/PIN timing, so it doesn't conflict with AD-6's "key-presence timing is never configurable" rule). Not promoting either primitive to a shared/standalone port method beyond `enroll_fido2_key`'s own new parameter yet — Rule of Three: revisit if/when Story 2.2 (revoke) turns out to need the same wait/enumerate primitive, at which point lifting the shared bits (e.g. the presence-wait poll) into a reusable `adapters::exec` helper is a small, low-risk move.
      - **This design is considered verified enough to resume implementation against.** Task 3 (and its currently-checked box) should be reopened/reworked to match the above; Task 4's CLI wiring needs the two new `enroll`-only flags; Task 6's tests need updating for the new prompt flow and the all-or-nothing flag validation. Story may move past `in-progress` once these are implemented and hardware-verified again.
