# Story 1.5: Create a File-Backed Tomb

Status: review

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a user with no prior FIDO2 experience,
I want to create a new tomb by giving a destination path and a size,
so that I don't need to manually pre-allocate a backing file before creating my tomb.

## Acceptance Criteria

1. **Given** a destination path that does not yet exist and a size, **when** I run the create command in file mode, **then** the tool allocates the backing file at that path sized as requested (`FilesystemBackend::set_backing_file_size`), formats it as LUKS2, creates the user-selected filesystem, and bootstrap-enrolls my first FIDO2 key, **and** the resulting LUKS2 volume is independently unlockable via bare `cryptsetup`/`fido2-token` (break-glass path) using the newly enrolled key, with the chosen filesystem mountable and ready to use. [Source: epics.md#Story 1.5]
2. **Given** a destination path that already exists, **when** I run the create command in file mode, **then** the tool refuses before touching anything — no file overwritten, no formatting attempted — with a clear message. [Source: epics.md#Story 1.5]
3. **Given** the create workflow internally, **when** it runs, **then** it generates a transient random passphrase in a `zeroize::Zeroizing` buffer to seed `luksFormat`/`luksOpen`, wipes it immediately after use and before `mkfs` runs, and removes the transient bootstrap keyslot via the guarded last-keyslot-safe removal primitive once the real FIDO2 key is enrolled, **and** the enrolled FIDO2 key's metadata is written as generic token fields `key_label`/`filesystem` — never prefixed with the product's placeholder name. [Source: epics.md#Story 1.5, AD-2, AD-3, AD-5, AD-9, AD-13]

- **Sequencing inversion vs. AD-5's prose:** AD-5 is written assuming the last-keyslot guard already exists when CAP-8 (this story) needs it — in prose it says CAP-8's bootstrap cleanup "reuses" the guard. In this project's actual roadmap, Story 1.5 (CAP-8) is built *before* Story 2.2 (CAP-3/revoke). This story must therefore originate the shared guarded-removal primitive as reusable `domain` code; Story 2.2 will be the one reusing it later. Do not write a `create`-only inline version of the guard logic — that would force Story 2.2 to duplicate or refactor it. [Source: ARCHITECTURE-SPINE.md#AD-5]

### Completion Notes List

- **Post-review UX fixes, from real user feedback after running the compiled binary.** After the story reached `review` and the user tried `tomb-fido2 create` for real, three usability issues surfaced and were fixed before merge:
  1. **The whole command required running as root.** Investigated which operations actually need it: only `cryptsetup luksOpen` (creates the dm-crypt mapping) and `mkfs.ext4` (writes to that mapper device) genuinely need root — `luksFormat`, FIDO2 enrollment, and token/keyslot cleanup all operate directly on the LUKS2 header file and need no elevation (confirmed empirically in Task 1's spike, which ran unprivileged). Added a `privileged()` helper (`adapters/exec/mod.rs`) that prefixes only those two calls with `sudo`, which prompts interactively via the controlling terminal exactly when reached — chosen over auto-detecting/invoking `pkexec` (no GUI use case for this CLI-only tool) or a setuid binary/privileged daemon (much heavier for v1). `sudo` is now a preflight-checked `LuksBackend` dependency.
  2. **`create` never closed the LUKS mapping.** It left the tomb open (mapped, unmounted) indefinitely after finishing — inconsistent with a cold-storage tool's expected lifecycle, and the reason a real `create::run` run left a `vault-*` dm-crypt mapping open on the test machine (a previous hardware run's manual `cryptsetup open` used an unrelated ad hoc name, so it didn't collide with the leaked one, but the leak was real). Added `LuksBackend::close(mapper)` (wraps `cryptsetup close <name>`, also needs `sudo`) and `create::run` now calls it as the final step after the guarded keyslot removal — `create` never mounts anything itself, so there's nothing to unmount first. Any `vault-*` mapping left open by an earlier (pre-fix) hardware run is now stale and should be closed manually (`sudo dmsetup ls` / `sudo cryptsetup close <name>`).
  3. **CLI ergonomics:** `--size` now accepts an optional K/M/G/T suffix (binary, powers of 1024 — matching `resize2fs`/`lvreduce` convention) via a small custom clap value parser (`parse_size` in `cli/main.rs`), falling back to a plain byte count with no suffix. `--filesystem` is now optional, defaulting to `ext4` (the only v1-supported value) via clap's `default_value`.
  - All 3 fixes are CLI/adapter-layer only; no change to `CreateTarget`/`Filesystem`/AC-facing domain types beyond the new `LuksBackend::close` port method. Unit tests updated: `FakeLuksBackend` gained a `close` fake (logged like every other call), and the happy-path ordering test now expects `close` as the final entry.
