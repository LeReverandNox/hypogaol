### Significant technical events

- **Story 6.5's lock mechanism was wrong twice before it was right.** The architecture (AD-20) specified `flock(2)`. Live testing found `cryptsetup` takes its own internal LUKS2 container lock for nearly every operation, including read-only ones — an `flock`-based guard held for a whole workflow self-deadlocked against the tool's own next subprocess call. A `--disable-locks` patch fixed `cryptsetup` specifically; further live testing then found `systemd-cryptenroll` (used by `enroll`) has the same internal-locking behavior with no equivalent override flag at all. The mechanism was replaced entirely, live, with a Linux abstract-namespace `AF_UNIX` socket — a kernel-only resource that can never collide with either tool's internal locking. AD-20 was rewritten to describe what actually shipped.
- **Story 6.4 found undocumented real-world filesystem floors.** `mkfs.xfs` refuses under ~300MB; the Btrfs kernel resize ioctl refuses to shrink-target under 256MB. Neither was in the architecture spine or any upstream doc consulted beforehand; both were found via real hardware runs post-review and patched into `create`/`resize`'s size checks (`size_floor_for`, `MIN_BTRFS_RESIZE_PAYLOAD_BYTES`).
- **Story 6.7 found a real clap parsing gap**: short-flag clustering (e.g. `-fu`) silently swallows the next short flag as the first one's value — standard getopt behavior, not a defect, but a real footgun for `-u`/`--user-verification`. Mitigated via a doc-comment warning rather than a code change (a deliberate trade-off, not an oversight).
- **Story 6.8 found the repo was actually private** at verification time, 404-ing every `github.com`-hosted badge/link — caught only because every URL was curled, not just written.

## What Went Well

- **Hardware-verification discipline held for the entire epic.** Every story stated explicitly what could and couldn't be verified without real hardware; LeReverandNox followed up on essentially every flagged gap. Only one was still open going into this retro (6.1's crash-simulation), and it turned out to already be resolved and simply unsynced.
- **Two long-standing recurring-pattern watches (marker-bleed, untested-parsing-functions) became genuinely internalized practice**, not just repeatedly-caught mistakes — proactive application with zero fresh incidents across multiple stories each.
- **A genuinely wrong architectural decision (AD-20's `flock` design) was caught and fixed within the same story**, via real, disciplined, incremental hardware testing rather than shipping and discovering it in production. The replacement mechanism (abstract-namespace socket) required zero changes to the port abstraction, `LockGuard`'s shape, or any existing test — the boundary was drawn in the right place even though the implementation behind it was wrong twice.
- **Story 6.4's real-hardware-discovered filesystem floors got turned into permanent domain-level guards**, not just fixed once and left implicit — future users get a clear pre-`mkfs`/pre-`growfs` rejection instead of an opaque tool-level failure.

## What Didn't Go As Smoothly

- **Self-reported test-count/baseline drift, six stories in a row (6.2–6.7).** Each story's own Completion Notes cited a baseline or final count that turned out to be wrong when the next story re-verified it from scratch. Never caused a real problem — the re-verification discipline caught every instance — but it's pure repeated overhead solving the same problem by hand each time.
- **Tracker drift, found three times in this retro alone.** Two release-pipeline verifications and one hardware crash-simulation were all genuinely completed — one of them weeks before this retro — but the `sprint-status.yaml` `action_items` list never got updated to match. Distinct from Epic 1's old "story Status header not synced" problem: this is a second location (the action-items list) that can independently go stale even when the story file itself is accurate.
- **AD-20's underlying assumption (that `flock` would coexist cleanly with `cryptsetup`/`systemd-cryptenroll`) was never something the architecture-design step could have caught without hardware** — not a process failure, but worth remembering as a class of risk: OS-level subprocess-locking interactions are the kind of thing this project's design phase can't fully de-risk on paper.
